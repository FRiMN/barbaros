# Версионирование приложения (для разработчиков)

Этот документ описывает, как в Barbaros формируется и используется номер версии. Он полезен при сборке, релизах и при изменении окна «О программе» (`AboutWindow`).

## Принцип работы

Версионирование построено на плагине **[setuptools_scm](https://github.com/pypa/setuptools_scm)**, 
который берёт версию напрямую из истории Git (тегов). В `pyproject.toml` это настроено так:

```toml
[project]
dynamic = ["version"]

[build-system]
requires = ["setuptools>=61", "setuptools-scm"]
build-backend = "setuptools.build_meta"

[tool.setuptools_scm]
write_to = "src/barbaros/__version__.py"
```

При каждой сборке (`uv build`, `uv run invoke build_python` и т.д.) setuptools_scm генерирует файл `src/barbaros/__version__.py` со значениями, вычисленными из ближайшего тегa.

## Формат версии

Проект использует **календарное версионирование (CalVer)** вида:

```
YYYY.M.D
```

Где:

- `YYYY` — год (например, `2025`);
- `M` — порядковый номер месяца (`1`–`12`);
- `D` — **порядковый номер релиза** в рамках этого года и месяца (`0`, `1`, `2`, …), а **не** день месяца.

Например: `2025.10.0` — первый релиз за октябрь 2025 года, `2025.9.1` — второй релиз за сентябрь.

Теги в репозитории имеют префикс `v`: `v2025.10.0`, `v2025.9.2` и т.п. (см. `git tag`). Обратите внимание: `D` увеличивается с каждым релизом в месяце и никак не привязан к календарному числу.

Для сборок, сделанных **не по тегу** (например, из произвольного коммита), setuptools_scm добавляет суффиксы с номером коммита и хешем:

```
2025.10.1.dev148+g599f46f6f.d20260815
```

- `dev148` — количество коммитов поверх последнего тега;
- `g599f46f6f` — короткий хеш коммита;
- `d20260815` — дата сборки.

Таким образом версия из релизного тега выглядит «чистой» (`2025.10.1`), а версия из разработческой ветки — с указанием промежуточного состояния.

## Сгенерированный файл `__version__.py`

Файл `src/barbaros/__version__.py` **генерируется автоматически** и **не должен правиться вручную и коммититься**. 

Он уже добавлен в `.gitignore` (строка `__version__.py`), поэтому попадёт в сборку, но не в репозиторий. Если файл отсутствует (например, после чистого клона до сборки), импорт `from .__version__ import version` упадёт — сначала нужно выполнить сборку пакета.

### Экспортируемые символы

```python
version: str            # "2025.10.1.dev148+g599f46f6f.d20260815"
__version__: str        # то же, что version
version_tuple: tuple    # (2025, 10, 1, 'dev148', 'g599f46f6f.d20260815')
__version_tuple__: tuple
commit_id: str | None   # 'g599f46f6f'
__commit_id__: str | None
```

## Как сделать релиз

1. Убедитесь, что изменения закоммичены в `main`.
2. Создайте и запушьте тег в формате `vYYYY.M.D`, например:

   ```sh
   git tag v2025.10.2
   git push origin v2025.10.2
   ```

3. При сборке по этому тегу `version` станет чистым (`2025.10.2`), без dev/commit-суффиксов.
4. Соберите пакет и Flatpak (см. [build_flatpak.md](build_flatpak.md) и `tasks.py`).
5. Создайте релиз в GitHub и прикрепите собранные пакеты.

Для предрелизных сборок можно использовать теги с суффиксом, например `v2025.8.6.rc1` (такие теги уже есть в истории).

## Связь со сборкой Flatpak

Имя итогового `.flatpak`-bundle формируется из версии собранного wheel-файла. 
В `tasks.py` задача `bundle` извлекает версию из имени файла `dist/barbaros-*.whl` и создаёт, например, `dist/barbaros-2025.10.1.flatpak`:

```python
version = c.run("ls dist/barbaros-*.whl | head -1 | sed 's/.*barbaros-\\([^-]*\\).*/\\1/'", hide=True).stdout.strip()
c.run(f"flatpak build-bundle -vv repo dist/barbaros-{version}.flatpak io.github.frimn.barbaros")
```

То есть версия, показываемая в `AboutWindow`, совпадает с версией в названии установочного файла и в метаданных пакета.
